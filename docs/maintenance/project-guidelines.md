Law-driven decision points and the tax-law archive live under `docs/maintenance/tax/`; domain guidelines (crypto rules, reporting guidelines, Koinly, lessons) live directly under `docs/maintenance/`.

Layer 3 history subdirectories have distinct semantics; place a file by lifecycle stage, not by topic:
- `feature-notes/` (`rfcs_dir`) holds **active** RFCs / PRDs / proposals for improvement only. When an RFC lands (all phases shipped) or is superseded/frozen, move the file to `context/` (load-bearing reference / provenance material) or `investigations/` (post-mortems / one-time audits) so `feature-notes/` stays a clean "what's still on the table" view. Keep the date prefix when moving (citation sweep is a pure path-substitution); investigate-destination precedent (`aggregate-crypto-rewards-review-analysis.md`) uses non-prefixed names with a `**Date** / **Branch** / **Plan**` metadata block instead.
- `context/` holds load-bearing reference material and frozen artifacts cited by active maintenance docs (e.g. landed-RFC provenance for tax rules, frozen audit snapshots of deleted files).
- `investigations/` holds completed post-mortems and one-time analysis notes.
- `plans/completed/` is the archive for executed implementation plans; `migrations/` for one-time migration records.

1. Every downloaded external source mirrored under `docs/.../official/` must have a corresponding `sources.md` entry that records the official URL, issuing date, effective date (when the source takes legal effect; defaults to issuing date if not separately specified), superseded date (when replaced by a newer enactment; `-` when still current), retrieval date, purpose, and the exact articles, sections, annexes, chapters, or clauses relied on. Publication date alone does not determine when a law applies; a source published in 2023 may take effect in 2025, and a 2024 enactment may supersede a 2021 law. The effective/superseded chain is what determines which sources govern a given fiscal year. Each time an archived external source is used for analysis, implementation, or user-facing advice, check the official source first for a newer version. If a newer official version exists, archive it in the correct folder and update the manifest before relying on that source.

2. Tax treatment decision points live in `docs/maintenance/tax/decision_points/<year>.md`, one file per fiscal year. Each file is a self-contained snapshot listing which laws are in effect for that year (with effective/superseded dates), the per-country decision-point table, and source references. A `README.md` index lists all fiscal years and provides a template for creating new ones. When starting a new fiscal year, copy the latest year file, re-verify each decision point against current sources in `docs/maintenance/tax/laws/`, and update the laws-in-effect table. When a law or interpretation has not changed, the new file may reference the prior year for unchanged rows rather than repeating full rationale.

   Each `<year>.md` has a machine-readable companion `<year>.toml` in the same directory. The TOML is the runtime sidecar consumed by `config.py`; it encodes law-driven boolean flags per country (e.g. `exclude_loan_repayment_gains`). When a decision point changes (new year or amended law), update **both** files together: the `.md` for the human-readable rationale and the `.toml` for the machine-readable flags. `config.ini` does not contain law-driven flags; those live exclusively in the TOML sidecar.

3. AT guidance documents (folheto, PIVs, ofícios circulados) may cite CIRS paragraph numbers from before a renumbering amendment. When consulting any AT guidance that cites a CIRS paragraph number, cross-check the number against the current consolidated CIRS PDF **mirrored at `docs/maintenance/tax/laws/pt/official/`** (file `cirs_consolidado_<ultima-atualizacao-date>.pdf`; provenance and the current redação tag in `docs/maintenance/tax/laws/pt/sources.md`, entry 4). The CPPT (`cppt_consolidado_*.pdf`, entry 5) and CIS (`cis_consolidado_*.pdf`, entry 6) consolidated codes are mirrored alongside it for the same offline-verification reason (reclamação/impugnação prazos; CLS legal base). The consolidated PDF includes inline annotations such as "(Anterior n.º 7 - Lei n.º 31/2024)" that make renaming explicit. Whenever a renumbering is discovered, update all affected references in `sources.md` "Relevant provisions consulted" fields, decision point notes, and `platform-divergences.md` in the same pass. The consolidated CIRS is always the authoritative current numbering; AT documents are authoritative on interpretation but may lag on paragraph numbering.

4. Multi-agent code review catches critical bugs that single-reviewer passes miss. The FIFO rebuild implementation (2026-05-27) required multiple review iterations: fixes in one pass revealed new issues. Always verify review findings against actual code state, not assumptions from prior iterations. Critical bugs found during review:
   - Fee unit errors (using crypto quantity instead of EUR value for cost basis)
   - Temporal FIFO violations (future-dated lots consumed by past disposals)
   - Empty string handling corrupting aggregation results
   - Missing review flags on zero-cost pool exhaustion

   Code review must examine the actual diff and source files in each iteration; summaries from prior passes become stale as code changes.

5. **Data handling: missing vs invalid.** Treat missing and invalid data differently.

   **Missing data** (supplementary info absent but can be added manually later: ISIN, country, security details): process with clear error indicators. Always log an `ERROR` with actionable guidance, include the record in output with a visible sentinel (`"MISSING_ISIN_REQUIRES_ATTENTION"`, `"UNKNOWN_COUNTRY"`), highlight in Excel, and never lose monetary amounts due to missing supplementary info.

   **Invalid data** (format corrupted, non-numeric amounts, required columns absent, broken structure): fail fast with a `FileProcessingError` containing row number, field, and expected format. Use exception chaining (`from e`). Do not continue processing with corrupted data.

   Key principles: never silently skip expected data; preserve financial integrity; distinguish missing (warn and continue) from invalid (stop immediately). Log with parameterised format (`logger.error("Row %d: bad value %s", row, val)`); raise with f-strings (`raise FileProcessingError(f"Row {row}: bad value {val}")`).

6. **External-report naive dates are jurisdiction-local, not UTC.** Koinly's Capital Gains / Other Gains / Income `Date` columns are wall-clock local time (mainland-Portugal WET/WEST), proven by their ~0h winter / ~+1h summer offset versus the explicit-UTC Transaction History twins. Never assume a naive date equals UTC: a `strptime` format literal like ` UTC` does not populate `tzinfo`, so the naive and explicit-UTC formats are indistinguishable on `parsed.tzinfo`. Localize naive dates to the jurisdiction IANA zone (`IANA_TIMEZONE` in `config.ini` `[TAX JURISDICTION]`, resolved once at config load into a `ZoneInfo` on `TaxJurisdictionConfig.timezone` and threaded to the parser; default `Europe/Lisbon` for PT), convert to UTC at ingestion via `zoneinfo` (which owns DST transitions historically; never hand-code transition days), and leave explicit-UTC dates unchanged. A zone is MANDATORY to localize naive dates, so the application enforces a STRICT fail-fast: when crypto data is present and the timezone cannot be resolved, the crypto-loading boundary `_load_crypto_tax_report` (`application/run_report.py`) raises `ConfigurationError` - this covers BOTH a configured jurisdiction whose timezone is `None` (any non-PT country without `IANA_TIMEZONE`; PT auto-deduces `Europe/Lisbon`) AND the no-config path (`jurisdiction is None`, e.g. `config.ini` absent). `_main` propagates that `ConfigurationError` unwrapped (it is not degraded to "continue without crypto" nor wrapped into `ReportGenerationError`). The loader `load_koinly_crypto_report` itself stays a pure parser, unit-testable with `jurisdiction=None`; the no-zone silent-UTC-stamp is a deliberate library affordance in `parse_koinly_datetime`, NOT the application default. This keeps every calendar-day cross-report match key (DP-014 payment match, derivatives dedup, OGR override) on the true-UTC day; see `docs/maintenance/koinly_guidelines.md` Section 5.
7. **High-volume per-row warning grouping (per-row DEBUG + aggregate INFO/WARNING).** **Governing principle:** console WARNINGs are reserved for *project/processing* problems only; every *data issue* (per-row anomaly attributable to the source export or pipeline edge case) and every *methodology decision* (dedup, materiality filter, OGR routing) lives in the user-facing Excel extract - either as `CryptoReviewEntry` rows in Crypto Supplementary's "Review required" section or as a run-specific count cell in the Assumptions & Methodology (A&M) sheet. The console is the signal that "something is wrong with the project or the way it processes data"; the extract is the place for the user to see every data issue and every decision applied to their records. A console WARNING that merely announces a count of items the user can already see in the extract duplicates the audit surface and is demoted to aggregate `logger.info(...)`. When a warning is emitted once per input row inside a loop AND its per-row detail is already surfaced in the user-facing Excel review list (`CryptoReviewEntry`, `CryptoFifoRealization(review_required=True)`, `DerivativesPnLEntry`), the per-row emission MUST be downgraded to `logger.debug(...)` and grouped into ONE aggregate `logger.warning(...)` (or `logger.info(...)`, per the four-class taxonomy below) summary emitted after the loop, naming the total count and distinct-key breakdown (canonical pattern A: per-row `logger.debug(...)` + aggregate `logger.info(...)` in `crypto_reporting.py` `_parse_capital_gains_file` (the `Flagged %d all-zero capital gains row(s)` `logger.info`); canonical pattern W9 (the EXTRACT_SURFACED shape): per-row `logger.debug(...)` + aggregate `logger.info(...)` + appended `CryptoReviewEntry` rows in `crypto/ogr_handler.py` `_split_ogr_index` (the `OGR row(s) routed to derivatives` aggregate `logger.info`)). Per-row detail stays reachable via the file handler (`logs/tax-reporting.log`, hardcoded to `DEBUG`), so the conversion never deletes the per-row emission - it only lowers its level. The aggregate WARNING preserves the warning-level audit signal on the console (the "data-loss conditions must be logged at warning+" rule still holds; it is satisfied by the aggregate, not the per-row). Sites that have NO Excel review-list surface (DATA_DROPPED / PARSE_ERROR / INVARIANT_VIOLATION / RECONCILIATION warnings such as non-positive acquisitions / negative consumptions, pattern O) MUST NOT be fully downgraded to DEBUG-only: because there is no Excel review cell to carry the audit signal, they retain a MANDATORY warning-level signal. They use a group-collapse (per-row DEBUG + ONE aggregate WARNING): the per-row detail is `logger.debug(...)` but the aggregate `logger.warning(...)` summary is the audit trail and must stay WARNING. This is the DEVELOPER_ACTIONABLE class (pattern O). The "data-loss conditions must be logged at warning+" rule is satisfied by the aggregate WARNING, never by dropping the warning-level signal entirely. The per-class target level is decided by the four-class taxonomy below (a site whose per-row anomaly sets `review_required=True` + `review_reason` on a rendered entry, such as the cross-asset deferred-acquisition and transfer carry-over sites in patterns J/K, is HAS_EXCEL_SURFACE and demotes its aggregate to INFO; a pure-level demotion with no surface such as pattern I / W8 is INFO (outside the four-class taxonomy; see footnote †); a developer-actionable data-loss site such as pattern O stays WARNING). Aggregated entries with pool-exhausted placeholder acquisition dates likewise follow the per-row-DEBUG + aggregate-INFO convention (pattern L). When the accumulator lives on a shared instance mutated from multiple caller loops (e.g. `TokenOriginResolver._disagreements`), add an instance `Counter`, increment it instead of warning in the per-row branch, expose `log_and_reset_disagreements(scope)` which emits-then-clears (clear AFTER emit, unconditional), and have each caller invoke it after its loop with a distinct scope label in call order. The console log level is configurable via `LOG_LEVEL` in `config.ini` `[COMMON]` (default `WARNING`); the file handler always captures `DEBUG`.

   **Four-class taxonomy (applies to every per-row WARNING inside a loop).** Each site is classified into exactly one of four classes BEFORE choosing the level. The class is derived by tracing the site's output through ALL branches of the pipeline to the rendered Excel review cell OR to a separately emitted extract surface (a `CryptoReviewEntry` row or A&M count), not by reading the emitter line or tracing only the happy path (see lesson on bucket-assignment tracing).

   - **Class EXPECTED_BEHAVIOR:** the warning describes CORRECT tax treatment with no anomaly and no downstream `review_required` flag. Target: `logger.info(...)` (or `logger.debug(...)` when fully expected). Example: a third-currency fee correctly folded into `AcquisitionContext.fee_eur` and consumed into `cost_eur` inside `crypto_fifo/matching.py` `_build_taxable_realization` (`cost_eur=proportional_cost + proportional_acq_fee`).
   - **Class HAS_EXCEL_SURFACE:** the warning's anomaly sets `review_required=True` + `review_reason` on an entry whose DATA TYPE renders a review column in the Excel report (`CryptoFifoRealization` / `CryptoCapitalGainEntry` / `CryptoReviewEntry` / `DerivativesPnLEntry`), regardless of per-row `review_required` values. **Classification is by the entry's schema, not by runtime values** (a blank cell for a clean row still counts as a surface; premortem M2). Target: per-row `logger.debug(...)` + ONE aggregate `logger.info(...)`. The **Excel cell is the canonical audit surface**; the console aggregate at INFO is a nicety (reachable at `LOG_LEVEL=INFO`), NOT the audit trail. An `AcquisitionContext.review_reason` is an intermediate application field, NOT a rendered schema field, so a site that sets the flag only on an intermediate (a deposit lot that may never be disposed) is NOT HAS_EXCEL_SURFACE unless every such row is guaranteed to produce a realized entry.
   - **Class DEVELOPER_ACTIONABLE:** data loss or anomaly with NO Excel surface. Stays `logger.warning(...)`. Per-row sites inside loops get grouped (per-row DEBUG + ONE aggregate WARNING) so the warning-level signal survives without flooding. The aggregate WARNING IS the audit trail here (the opposite of HAS_EXCEL_SURFACE, where the cell is).
   - **Class EXTRACT_SURFACED:** the warning's anomaly or decision has NO rendered cell on its own entry type, but the same per-row detail is made visible in the extract by EMITTING A SEPARATE `CryptoReviewEntry` row (in Crypto Supplementary's "Review required" section) or a run-specific COUNT SUFFIX on an existing A&M methodology item. Distinct from HAS_EXCEL_SURFACE: HAS_EXCEL_SURFACE means the per-row entry's OWN schema renders a review cell (no new rows are added - only the console aggregate drops to INFO); EXTRACT_SURFACED means there is no per-row review cell, so the pipeline ADDS review rows or an A&M count to carry the signal. Target: per-row `logger.debug(...)` + ONE aggregate `logger.info(...)` + the extract surface (review rows OR A&M count). The aggregate INFO is a nicety (reachable at `LOG_LEVEL=INFO`); the EXTRACT SURFACE is the canonical audit trail, mirroring HAS_EXCEL_SURFACE's "Excel cell is the canonical audit surface" rule. Two sub-shapes: (a) per-row data issues (W1/W2/W3/W5/W9, plus the removed lots (`is_suspicious=False` for tagged/embedded W6/W7 lots; `is_suspicious=True` for the W7 untagged-whitelisted removed branch which carries W8's verify-network-fee signal), surplus, and malformed sub-lists of W6/W7) emit one `CryptoReviewEntry` per affected row; (b) methodology decisions whose individual rows are intentionally discarded emit an A&M count cell: W10's sub-1-EUR filter renders a PT-C-028 count suffix (e.g. `... [This run: filtered 173 entries, 8 retained.]`), and the W6/W7 removed-lots dedup renders a separate dedup count cell (e.g. `[This run: derivatives removed N; fee removed M.]`) alongside the review rows from (a). A site whose per-row detail lives on an intermediate application field that may never be realized (e.g. W3's zero-NV deposit setting `review_reason` on an `AcquisitionContext` held to year-end) is NOT HAS_EXCEL_SURFACE - it is EXTRACT_SURFACED because the explicit review row makes the surface independent of later realization.

   **Native-gas split inside EXPECTED_BEHAVIOR (Bucket A-split).** The third-currency-fee site in `crypto_fifo/_emitters.py` (`_handle_exchange` / `_emit_sent_only_exchange`, the `fee in third currency` leg-check guarded by `is_native_gas_fee(...)`) is NOT uniformly expected. It applies a **unified two-model rule** (no explicit CEX/DEX branch needed); a third-currency fee is EXPECTED (no warning) when EITHER model holds:
   - **CEX model (existing leg-check, kept):** `fee_currency in (sent_currency, received_currency)` (a CEX deducts the fee from a trade leg).
   - **DEX model (new native-gas check):** `fee_currency == _CHAIN_NATIVE_FEE_ASSET[_derive_chain(wallet)]` (a DEX pays gas in the chain's native token; e.g. ETH gas on Ethereum, BNB on Binance Smart Chain, BERA on Berachain).
   It is **anomalous** (STAYS `logger.warning`) when the fee is NEITHER a leg NOR the chain's native gas (e.g. a USDC or governance-token fee), and **fail-safe STAYS WARNING when the chain is `"Unknown"`**. **Asset-keyed matching is unsafe** (ETH/BNB/MATIC are native gas on one chain but regular bridged tokens on others); the map MUST be chain-keyed, derived per-row. A flat "demote all third-currency fees to INFO" would silence genuinely anomalous third-token fees along with expected gas; the split preserves the WARNING for the anomalous case. See `docs/maintenance/crypto_implementation_guidelines.md` "Chain Derivation" for `_CHAIN_NATIVE_FEE_ASSET`.
