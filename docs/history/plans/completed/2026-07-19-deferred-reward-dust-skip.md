## Terms

- **Deferred dust** - a zero-value `DEFERRED_BY_LAW` reward row on an asset Koinly *can* price (the asset has at least one `value_eur > 0` row in `reward_entries`). The zero is a 2-decimal export rounding artifact. Collapsed into a per-`(asset, wallet)` "Suppressed zero-value deferred rewards" block on Section 3. Reuses the predecessor plan's "Reward dust" definition (CRG-021), extended to the deferred side.
- **Unpriced deferred reward** - a zero-value `DEFERRED_BY_LAW` reward row on an asset Koinly has *no* price feed for (every row for that asset in `reward_entries` is `value_eur == 0`). These currently carry `review_required=True` for the historical (now-rejected) reason "so the author can manually price each row." The grilling established there is no manual action the user can or should take: deferred rewards aren't taxed at receipt (CIRS art. 5(11)), and on disposal the FIFO pipeline reads the CG report and transaction history, never the reward row's `value_eur`. These rows collapse into the SAME single "Suppressed zero-value deferred rewards" block as deferred dust (informational, native-unit amount summed), distinguished by reason "unpriced"; not a review queue.
- **Parse-time skip** - the mechanism (mirroring `_KOINLY_TRACKING_TOKENS` FEE skip and `skipped_zero_value_tokens`): zero-value deferred reward rows are removed from `reward_entries` and relocated to a new `skipped_zero_value_deferred_rewards` list on the report. The list is the authoritative audit trail - every skipped row is retained with full fidelity. NOT a silent drop. (r1 review corrected the Terms claim that `skipped_assets` is a `Counter[tuple[str,str]]` - its production type is `dict[tuple[str,str], dict]`; the new `skipped_zero_value_deferred_rewards` mirrors the *convention* - pass a mutable container by reference and mutate it inside `_parse_income_file` - but is a `list[CryptoRewardIncomeEntry]` per Invariant 1, not a Counter.)
- **D2** - the design choice (vs. D1 presentation-only or D3 classification change): parse-time skip into a separate audit list, with render-time dust/unpriced block reading from that list. Chosen because (a) the platform-evidence check showed it's safe, (b) it cleans the data rather than hiding noise, (c) it makes the Section 4 `Total reward rows` count honest (the real non-zero deferred rows only, instead of the inflated total that includes zero-value noise), (d) tax math (`aggregate_taxable_rewards`, `reward_total_eur`) is unchanged because zero-value rows contribute nothing. The predecessor plan's "presentation-layer only" rationale was overcautious inheritance from Part 7; for the deferred side it had no real force.

## Gist & Examples

**Part A - Zero-value deferred rewards pollute `reward_entries` and the Section 3 detail table.** Today every zero-value deferred row renders in the Section 3 "DEFERRED BY LAW - SUPPORT DETAIL" table (split between dust and unpriced), each with a `YES:` review flag. The dust rows are 2-decimal rounding noise; the unpriced rows are assets the user cannot act on. Together they bury the real (non-zero) deferred rows the user actually wants to see, and inflate `Total reward rows (raw)` accordingly.

*Fix (D2 - parse-time skip).* In `_parse_income_file`, after classification, when `tax_classification == DEFERRED_BY_LAW AND value_eur == 0`, route the row to a new `skipped_zero_value_deferred_rewards` out-param (mirroring the existing `skipped_assets` out-param *convention* - pass a mutable container by reference and mutate it inside `_parse_income_file`; note `skipped_assets` is typed `dict[tuple[str,str], dict]` in production, not `Counter`) instead of appending to `reward_entries`. The skipped rows are retained as full `CryptoRewardIncomeEntry` objects (not count-only) so the render-time blocks can display per-`(asset, wallet)` detail and native-unit amount sums.

*Before/after on real fixture tokens.*

| Row | Today | After |
|-----|-------|-------|
| WBERA (illustrative priced-asset dust example), zero-value, deferred | in `reward_entries`; renders in Section 3 detail with `YES:` | skipped into `skipped_zero_value_deferred_rewards`; renders in the single "Suppressed zero-value deferred rewards" block (per-asset-wallet, summed native amount, reason "dust: Re-export with higher precision") |
| OSBGT (illustrative unpriced-asset example), zero-value, deferred | in `reward_entries`; renders in Section 3 detail with `YES:` | skipped into `skipped_zero_value_deferred_rewards`; renders in the SAME single "Suppressed zero-value deferred rewards" block (per-asset-wallet, summed native amount, reason "unpriced: no Koinly price feed; informational") |

| EUR reward, any value, taxable-now | in `reward_entries`; renders per CRG-021 (Part 7) partition | **unchanged** - Part 7 taxable-now partition is not touched |

*Why D2 (parse-time skip) and not D1 (presentation-layer partition).* The predecessor plan chose D1 for the taxable-now side because its rationale was "don't touch tax math." For the deferred side that rationale is hollow: deferred reward rows feed no tax computation. `aggregate_taxable_rewards` (`crypto/aggregation.py:94`) filters to `taxable_now` only; `reward_total_eur` sums `value_eur` (zeros contribute nothing); the only content reader is `assumptions_sheet._accumulate` for platform discovery, which the evidence check confirmed is unaffected. D2 cleans the data rather than hiding it.

**Part B - One "Suppressed zero-value deferred rewards" summary block on Section 3, with a per-row reason column.** Reads from `skipped_zero_value_deferred_rewards`. (r1 review collapsed the earlier two-block design - dust + unpriced - into one block per the simplification agent's "Not raised as findings" note: halves the helper count, loses no information as long as the reason column distinguishes the two failure modes.) The block is per-`(asset, wallet)`, sorted ascending, with one summary line per `(asset, wallet)` group carrying: count, summed native-unit `amount` (the `Amount` column, a `Decimal` on `CryptoRewardIncomeEntry.amount` at `entities.py:418`), summed `value_eur` (always `0.00` by definition, kept for format consistency with Part 7), and a **reason** ("dust: priced-asset rounding artifact, re-export with higher precision" vs "unpriced: no Koinly price feed, informational"). The `summed Value EUR` field is omitted (r2 review finding #8: definitionally constant `0.00` dead weight). No anomaly note above the block (r2 review dropped it - see "Dropped anomaly note" under Design Invariants). Both sums computed uniformly (no pattern-based exclusion - see "Dropped `_UNPRICED_NON_DISPOSEABLE_PATTERNS`" note under Design Invariants).

*Section 4 reconciliation.* `("Deferred-by-law rows (taxation deferred)", N)` is replaced by three lines:
- `("Deferred detail rows", D)` (the surviving non-zero deferred rows)
- `("Deferred dust rows (suppressed from detail)", M)`
- `("Deferred unpriced rows (suppressed from detail)", K)`

where `D + M + K == N` by construction (specific counts omitted here as personal portfolio data; the partition is deterministic and complementary).

(r1 review dropped a 4th `("Skipped zero-value deferred rewards (audit)", M+K)` line as tautological - `dust + unpriced == total` holds for any deterministic complementary-filter partition by construction; this is the same pattern the predecessor plan rejected at r4 Monitor #4. The single collapsed block renders both buckets; Section 4 still splits the count for auditability.)

`Deferred total value (EUR)` is unchanged (zeros contribute nothing). `Total reward rows (raw)` drops by the skipped-row count - this is the honest count and the visible user-facing delta of the plan.

## Design Invariants (CR Guard)

These invariants must not be compromised during implementation or code review:

1. **List preservation (user's hard requirement).** Every zero-value deferred reward row skipped at parse time is retained in `skipped_zero_value_deferred_rewards` as a full `CryptoRewardIncomeEntry` (not a count-only `CryptoSkippedZeroValueToken`). The Section 3 suppressed-rewards block renders per-`(asset, wallet)` from that list. A regression that silently drops rows (e.g. a future refactor that switches to count-only or forgets to populate the list) MUST fail the list-preservation test. *Rationale: the user's explicit requirement "we still get the list of the zero value and dust tokens/platform."*

2. **Tax math unchanged.** `aggregate_taxable_rewards` output, `reward_total_eur`, `taxable_now_total_eur`, `deferred_total_eur`, and the Reporting worksheet's OTHER CAPITAL INVESTMENT INCOME line are byte-for-byte identical pre- and post-skip. Justification (premortem-verified): `aggregate_taxable_rewards` filters to `taxable_now` (`aggregation.py:94`); `reward_total_eur` sums `value_eur` (zeros contribute `Decimal("0")`); deferred rewards don't reach the Reporting worksheet; and the FIFO/cost-basis path reads NEITHER `reward_entries` NOR `skipped_zero_value_deferred_rewards` (grep-clean across `crypto_fifo/`), so the skip is basis-neutral. The skip only removes zero-value rows that contributed nothing. *Rationale: D2 is viable precisely because the deferred zero-value rows feed no tax computation.*

3. **Discriminator unchanged from CRG-021, extracted as ONE shared helper.** Dust vs. unpriced splits on whether the asset has at least one `value_eur > 0` row anywhere in `reward_entries` (post-skip). `value_eur` is `Decimal` (non-optional) on `CryptoRewardIncomeEntry` (`entities.py:419`); `Decimal("0") == 0` is `True`. Genuinely-unpriced assets (every row zero) are unpriced; priced-asset zero rows are dust. The popular-token set is NOT the discriminator (it is the existing parse-time `is_known` gate; different concern). **The discriminator is extracted as ONE shared helper `_priced_assets_in_export(reward_entries) -> frozenset[str]` used by BOTH `_partition_taxable_now` and `_partition_skipped_rewards`** (AGENTS.md rule 30: "Sibling aggregators merging the same type must use byte-identical patterns or a shared helper"). The shared helper has a direct unit test. *Rationale: two hand-parallel comprehensions over `reward_entries` would silently desynchronize taxable-now dust from deferred dust on the next edit.*

4. **One summary block with per-row reason; native-unit amount summed with `:.8f` format (EUR sum dropped).** The single "Suppressed zero-value deferred rewards" block renders per-`(asset, wallet)`, sorted ascending (dust and unpriced groups merged into one sorted render - the partitions are disjoint by `(asset, wallet)`, so it's a dict-merge not an interleave), with a **reason** distinguishing "dust: priced-asset rounding artifact, re-export with higher precision" from "unpriced: no Koinly price feed, informational." Each line carries `count` and `summed amount` (native units, `CryptoRewardIncomeEntry.amount`) formatted with `:.8f` (r3 review finding #5: `parse_koinly_decimal` returns `Decimal(text)` verbatim; Koinly's variable-scale 2/6/8 dp Amount column produces inconsistent line text without a fixed spec; 8 dp matches Koinly's native precision) - the `summed Value EUR` field is DROPPED (r2 review: definitionally constant `0.00` dead weight; even Part 7's existing block has the same dead-weight field, two wrongs don't make a right). `safe_cell_value()` wrappers on all user-facing string interpolations. *Rationale (r1 + r2 + r3 review): collapsing two blocks into one halves the helper count while preserving the semantic split via the reason; the native-unit amount is the useful quantity for unpriced assets; the EUR sum conveyed no information the block title doesn't.*

5. **Compute-once-reuse (mirrors Part 7; code-review-enforced, not test-enforced).** `_partition_skipped_rewards` is called ONCE in `write_crypto_supplementary_sheet` (next to the existing `_partition_taxable_now` call at line 212), and the resulting `(dust_rows, unpriced_rows)` are passed into BOTH `_write_suppressed_deferred_rewards_block` (which takes pre-partitioned rows, NOT `reward_entries`) and the Section 4 reconciliation. Never re-partition for the reconciliation. (r2 review finding #5: abandons Part 7's compute-once-reuse invariant; a future discriminator edit would silently diverge Section 4's count from the rendered block.) **r3 caveat:** compute-once is a code-review invariant, not test-enforced; a double-compute implementation passes all tests (the function is pure). The call-counter test needed to pin it was rejected as over-engineering per the predecessor plan's r4 Monitor #4.

6. **CRG-021 amended, not contradicted.** CRG-021 (predecessor plan) says "presentation-layer only." This plan amends it to "taxable-now side is presentation-layer only; deferred side is parse-time skip (CRG-022)." The CRG-021 doc update makes the split explicit IN PLACE - Task 7 edits CRG-021's opening sentence to scope itself to the taxable-now side ("Reward dust partition for **taxable-now** rewards is presentation-layer...") and corrects the A2 accepted-risk text in place ("`reward_entries`... are unchanged **on the taxable-now side**; the deferred side is parse-time skip per CRG-022"), not as a trailing footnote. *Rationale (r1 review finding #12): the predecessor plan was itself mis-scoped by readers skimming CRG-021's header; a one-line footnote amendment repeats that failure mode. The two sides have different data-flow consequences (taxable-now rewards can feed `aggregate_taxable_rewards`; deferred rewards cannot); a single invariant would be wrong for one of them.*

### Dropped anomaly note (r2 review, 6-agent convergence)

An earlier draft of this plan included a one-line anomaly note above the suppressed-rewards block that fired when any skipped-list asset was in `popular_crypto_tokens.json`. **r2 review dropped it** (6-agent convergence: quality, testing, simplification, documentation ×2, security): on a real crypto-heavy portfolio, 13 of 15 dust head assets AND all 8 unpriced head assets are popular, so the note fired on ~99% of rows. Worse, the trigger contradicted itself across Gist/Invariant/Task 4 (dust+unpriced vs unpriced-only vs skipped-list-wide), and on dust rows it produced contradictory signals (note said "verify Koinly import" while the row's reason said "Re-export with higher precision"). The reason column already carries the actionable signal (dust → re-export; unpriced → informational), so the note added noise without information. If a narrower future signal is wanted, gate it on a whitelist of unambiguously-priceable major tokens (BTC/ETH/stablecoins) NOT in the Berachain-ecosystem bucket - that is a follow-up plan; out of scope here.

### Dropped platform-evidence guard (r1 review Critical #1)

An earlier draft of this plan proposed a parse-time platform-evidence guard (then-Invariant 4) that would keep zero-value deferred rows in `reward_entries` when their `(platform, wallet)` tuple was unique, defending future-year platform discovery. **r1 review dropped it** (5-agent convergence: quality Critical, testing High, implementation/architecture Medium, premortem Medium-High): the guard keyed on `(entry.platform, entry.wallet)` but the protected consumer `assumptions_sheet._accumulate` keys on `(origin.platform, origin.operator_entity)` - a completely different tuple. The guard's safety justification was false; its Task 1 test was non-discriminating (passed GREEN whether the guard protected the real consumer or not). The guard was also a no-op on real data and a layer crossing (`capital_entries` mutated 6 times between parse and report-construction). The narrow failure mode without the guard (a future-year wallet that accrues only zero-value deferred rewards vanishes from the Platform Assumptions manifest) is a visible, recoverable gap in a non-tax output, not a correctness defect. AGENTS.md line 83 contracts the Platform Assumptions tab as "a complete manifest. Do not filter" - if a real future-year gap surfaces, the structurally correct fix is to wire `skipped_zero_value_deferred_rewards` into `_collect_platform_summaries` as a fourth source (premortem's option c), not to add a parse-time guard. That is a follow-up plan; out of scope here.

### Dropped `_UNPRICED_NON_DISPOSEABLE_PATTERNS` (r1 review Medium #3)

An earlier draft of this plan proposed a `_UNPRICED_NON_DISPOSEABLE_PATTERNS = frozenset({"#", "POINTS", "REWARD AT"})` constant + set-contents test + substring filter to exclude NFT-position / points / claim-link tokens from the unpriced block's native-unit amount sum. **r1 review dropped it** (simplification Medium, reinforced by testing): (a) it is a no-op on real data - the plan's own real-data trace (line 9) enumerates every unpriced asset and none matches; (b) it filters a sum the plan itself declares non-actionable ("informational"). AGENTS.md line 123 ("Never introduce a hardcoded value without first flagging it") cuts against introducing values with no data showing they're needed. If NFT-position rows later pollute the informational display in a real future export, add a single substring rule (`"#" in asset`) at that point - `#` is the NFT-position convention and alone covers the dominant case with ~30% of the machinery.
