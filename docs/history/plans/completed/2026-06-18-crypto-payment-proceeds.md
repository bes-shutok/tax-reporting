## Terms

- **Alienação onerosa** - taxable disposal (PT-C-004). Selling crypto for fiat OR exchanging it for goods/services.
- **Valor de realização** - realization value, the EUR proceeds of a disposal (PT-C-007). For a goods/services purchase it equals the fair market value (FMV) of the crypto spent.
- **Payment (Koinly Tag)** - the Koinly tag on a disposal where crypto was spent to buy goods/services. Koinly records these as taxable disposals. The twin tag **Card Payment** covers card-spend disposals (absent from current data; future-proofing). The tag is data the tool can read from Transaction History.
- **Koinly zero-valuation** - for some payment disposals Koinly emits `Net Value (EUR) = 0` and shows "No market rates found for this asset" because its price DB does not recognise the imported ticker. The CG report then shows `Proceeds (EUR) = 0`, so the full cost basis surfaces as a phantom loss.
- **Token-rename alias** - the same asset imported under an outdated ticker. Worked example: a 1:1 EUR-pegged Circle stablecoin launched in 2022 as **EUROC**, since renamed to the canonical **EURC**. Koinly still holds the old `EUROC` label, which its price DB no longer matches - a typical root cause of the zero-valuation above. Both tickers denote the same EUR stablecoin.

## Gist & Examples

**Problem.** When crypto is spent to buy goods/services, Koinly tags the disposal `Payment` (or `Card Payment`). For most assets Koinly prices the disposed crypto normally and the Transaction History row carries a non-zero `Net Value (EUR)`. But for some assets - typically because of a token-rename alias or an unrecognised ticker - Koinly's price DB has no match, so it emits `Net Value (EUR) = 0` ("No market rates found"), and the Capital Gains report shows `Proceeds (EUR) = 0`. The tool reads proceeds = 0, the `cost > 0 AND proceeds = 0` branch of `_build_zero_basis_review_reason` flags it, but the entry still reaches the report carrying the full cost basis as a **phantom loss**.

**Fix (three-tier proceeds resolution).** For a disposal whose CG proceeds is 0, recover the `Payment`/`Card Payment` tag by correlating the CG row to its TH row, then resolve proceeds in a fixed order - tier 1 (Koinly's own value), tier 2 (stablecoin-pegged resolution: EUR par OR year-end rate), tier 3 (review flag):

1. **Tier 1 - Primary: trust Koinly's own value.** If the matched TH row has `Net Value (EUR) > 0`, proceeds = that value (the real FMV; works for any asset Koinly prices; no estimation). This is the path that handles USD-pegged stablecoins (USDT/USDC/DAI) - Koinly prices them directly.
2. **Tier 2 - Fallback: stablecoin-pegged resolution (when Koinly had no market rate, `Net Value (EUR) == 0`).** Look up the asset in the stablecoin reference data (reused from `docs/maintenance/tax/popular_crypto_tokens.json`, extended to cover popular stablecoins from Tether and Circle):
   - If the asset is a known stablecoin **pegged to EUR** (e.g. EUROC/EURC/EURT) - proceeds = the disposed amount at par (1:1 EUR), bounded by the peg assumption. It resolves the token-rename-alias case (the old `EUROC` label is recognised by our peg set regardless of Koinly's price DB).
   - If the asset is a known stablecoin **pegged to another fiat** (e.g. USDT/USDC/DAI pegged to USD) - proceeds = the disposed amount (taken at 1:1 to the peg) converted to EUR via the **fiscal year's end-of-year peg->EUR rate** from the SAME `[EXCHANGE RATES]` source shares/dividends already use (`config.ini`, parsed into `Config.rates` as `ConversionRate(base=EUR, calculated=<peg>, rate=...)`; applied `rate * amount = EUR`; this is the UNQUALIFIED `[EXCHANGE RATES]` section - the loader (`config.py:298`) reads ONLY that section and ignores archived `[EXCHANGE RATES YYYY]` sections - which the operator maintains as the fiscal year-end rate, the SAME convention shares/dividends use). The entry is `review_required=True` because this is an approximation (the stablecoin's peg AND the year-end rate both stand in for the disposal-date FMV), consistent with how EUR-par entries are flagged. If the peg currency has no rate in the config, this sub-case falls through to tier 3 (no auto-conversion).
3. **Tier 3 - Review flag (no proceeds inferred).** A non-EUR stablecoin whose peg currency has NO `[EXCHANGE RATES]` rate (the no-auto-conversion fall-through above), or any asset that is NOT a known stablecoin - leave proceeds = 0 and append a `CryptoReviewEntry` advising the user to check the asset's ticker mapping in Koinly (a zero valuation usually means Koinly could not match the ticker to its price DB).

**Gain recomputation (applies to every tier-1 / tier-2 correction):** `gain_loss_eur = proceeds - cost_eur`. The phantom full-cost loss must not survive.

Before/after (synthetic, EUR-pegged stablecoin, `Net Value = 0`):
- Before: `cost=100.00 proceeds=0 gain=-100.00 [YES: Zero disposal proceeds]`
- After: `cost=100.00 proceeds=100.00 gain=0.00` -> removed by the 1 EUR materiality filter; the review tab records "Payment purchase: proceeds inferred at EUR par (100.00) - Koinly reported no market rate; verify realization value".

Before/after (synthetic, priced asset, `Net Value = 120.00`):
- Before: `cost=100.00 proceeds=0 gain=-100.00 [YES: Zero disposal proceeds]`
- After: `cost=100.00 proceeds=120.00 gain=20.00` -> survives the materiality filter and reaches aggregation with the corrected, Koinly-sourced proceeds.

**Why primary-then-fallback, not blanket.** Koinly normally does price disposals; the zero is an asset-specific price-DB miss, not a property of payments. Using Koinly's `Net Value` whenever present avoids estimation entirely and works for any crypto (including USD-pegged stablecoins, which Koinly prices on the primary path). The fallback (only when `Net Value == 0`) resolves the unpriced stablecoin at EUR par (EUR-pegged) or via the fiscal year-end peg->EUR rate (other pegs, e.g. USD) - both `review_required=True` because they approximate the disposal-date FMV; non-stablecoins are flagged for ticker-mapping review. The year-end rate is the same source shares/dividends use, so the fallback is consistent with the repo's existing FX convention rather than introducing a new rate authority.

**Reuse, do not duplicate.** The stablecoin reference data reuses the existing `docs/maintenance/tax/popular_crypto_tokens.json`: its `tokens.stablecoins` list (extended with the missing EUR-pegged tickers) is the single membership source, and a new sibling `stablecoin_pegs` map annotates each stablecoin's peg fiat. The `payment_tags` live in the same file as a sibling. No new config file is introduced.

**Out of scope (tracked follow-up, reuses this correlation).** LP-token unstaking / "liquidity out" is a *different* treatment: non-taxable deferred per DP-005 / PT-C-005, to be **excluded**, not proceeds-corrected. It will reuse the CG<->TH tag correlation built here.

## Design Invariants (CR Guard)

1. **Correction is evidence-gated, never blanket.** Proceeds are inferred ONLY when (a) the CG row has `proceeds == 0`, AND (b) it positively matches a TH disposal row whose normalized Tag is in the configured payment-tag set (`payment`, `card payment`). **The TH tag index is built from payment-tagged rows ONLY** (so a non-payment sale can never collide into a payment slot). Any unmatched or non-payment zero-proceeds row keeps today's `_build_zero_basis_review_reason` flag unchanged. There is NO "known stablecoin" precondition on the gate - stablecoin membership only selects the fallback branch.
2. **The disposal stays taxable.** We correct the *valor de realização* (PT-C-007); we do not reclassify the event as non-taxable. Exclusion is reserved for the separate LP-unstaking case (DP-005).
3. **Correlation is collision-safe: ambiguity blocks correction, never guesses.** Match key is `(disposal_date_day, asset, normalized_platform, amount_6dp)` - deliberately NOT timestamp, because the CG "Date Sold" column carries local time with no timezone and the shared `parse_koinly_datetime` naively tags it UTC, while TH carries true UTC (observed sub-day offset). The day key pairs the CG calendar day with the TH calendar day (both wall-clock); this corrects **same-calendar-day** offsets only - a cross-midnight offset (a payment whose true-UTC TH row lands on the next calendar day) yields no match and falls to the DP-013 review flag (it is NOT "timezone-robust" unconditionally). Use a per-key `deque` + `popleft` (never `dict[key] = item`). **Correction uses a per-key count-equality rule, NOT a "remaining length" rule** (the latter makes the 2 CG + 2 TH case uncorrectable): pre-count BOTH sides per key BEFORE the entry loop, and the gate compares TWO STATIC PRE-COUNTS (NEITHER side may be a live deque length - see the static-vs-live note below). `cg_count[key]` = CG candidates (entries with `proceeds_eur == 0` AND `asset NOT in loan_affected_assets` - the SAME population the loop iterates, so a loan-affected zero-proceeds sibling on the key does NOT inflate the count and block an unrelated candidate). `th_count[key] = len(tag_index[key])` = payment-tagged TH rows on the key, captured ONCE when `tag_index` is built and BEFORE any `popleft` shrinks it. For each candidate: if the key has NO payment-tagged TH row (`th_count[key] == 0`) -> leave unchanged, no new review entry (the DP-013 flag already covers it - "unmatched != no-market-rate"); elif `cg_count[key] == th_count[key]` -> correct, popping one TH index in iteration order (1:1 and N:N both pair cleanly; N>1 pairing is POSITIONAL by report order, mirroring the repo's own `derivatives_dedup` precedent - totals are conserved, per-lot attribution may be arbitrary for genuinely-distinct same-key payments, flagged in Monitor); else (counts differ in either direction) -> leave ALL candidates on that key unchanged and append ONE `CryptoReviewEntry` for the key (not one per row) naming the count mismatch. The ">1 in bucket" condition alone does NOT block correction - it blocks only when it makes counts unequal. **Static-vs-live invariant (r10 concurrency Blocker): the count-equality gate MUST compare two PRE-COUNTS captured before the entry loop. `th_count[key]` is NOT a live `len(bucket)` read per candidate - the success-path `bucket.popleft()` shrinks the shared deque by one, so a live `len(bucket)` UNDERCOUNTS after the first pop: on the 2 CG + 2 TH case the FIRST candidate passes the gate (`2 == 2`), pops, then the SECOND candidate reads `len(bucket) == 1` against the still-static `cg_count[key] == 2` and (falsely) routes to the count-mismatch branch - leaving the second CG uncorrected and emitting a spurious "ambiguous" review for a perfectly count-matched key, so `second_cg_row_consumes_leftover_in_order` cannot pass under a live-length gate. (The r5 count-equality fold introduced this live-vs-static defect; the cited `derivatives_dedup` precedent does NOT count-match - it pops unconditionally - so its correctness does not transfer.) Build `th_count[key] = len(tag_index[key])` once when constructing the tag index (alongside `cg_count`); the live deque is used ONLY for the `popleft`, and the "no TH row" early-out reads the static `th_count[key] == 0`.** Wrong proceeds never ships with only a log line.
4. **Proceeds resolution order is fixed: Koinly value first, then stablecoin-at-par (EUR) / stablecoin-via-year-end-rate (other peg), everything else a review flag.** Read the matched TH row's `Net Value (EUR)`; if it is finite AND `> 0` use it (a NON-finite value - `inf`/`nan`, which `parse_koinly_decimal` accepts as a valid Decimal - is treated as MALFORMED: warn naming "non-finite Net Value", leave the entry unchanged with its DP-013 flag, do NOT infer; `Decimal("inf") > 0 == True` would otherwise ship `proceeds = Infinity`, the same silent-corruption class as the peg_rate guard - r9 security Medium); else look the asset up in the stablecoin reference data: a known **EUR-pegged** stablecoin -> `amount` at par; a known **non-EUR-pegged** stablecoin whose peg currency HAS a rate in `Config.rates` -> `amount * year_end_rate(peg->EUR)`; a known stablecoin whose peg currency has NO rate in config -> do not infer, specific review reason naming the peg and the missing rate; not a known stablecoin -> do not infer, generic review reason. A non-zero `Net Value` is never overridden by the fallback. **Both stablecoin fallbacks are approximations of the disposal-date FMV** (PT-C-007), `review_required=True`: (a) EUR-par assumes the 1:1 peg held on the disposal date (EURC/EUROC/EURT are issuer IOUs, not legal-tender EUR, and can depeg); (b) the year-end peg->EUR rate (`[EXCHANGE RATES]`, the SAME source shares/dividends use) assumes the peg held 1:1 AND approximates the disposal-date FX rate with the fiscal year-end rate. Every fallback-corrected entry's reason NAMES its assumption (par, or peg + rate + "year-end rate, verify") so a depeg or stale rate is not silently shipped; a sub-EUR approximation-driven gain/loss being removed by the materiality filter is itself a masking risk tracked in Monitor.
5. **Gain is recomputed, not inherited.** After setting proceeds, `gain_loss_eur = proceeds_eur - cost_eur`. Koinly's phantom loss (computed from its proceeds=0) must not survive.
6. **Inference is visible, survives the materiality filter, and is injection-safe everywhere it is emitted.** Corrected entries carry `review_required=True` with a specific reason naming the asset, the proceeds, the resolution source ("Koinly Net Value" or "EUR par"), and the Koinly data gap; the function also appends a `CryptoReviewEntry` to the shared `review_entries` list. Non-EUR-stablecoin and non-stablecoin fallbacks append their own specific review entries. **Two RAW-rendering sinks consume these strings without `safe_cell_value`:** the capital-entry `review_reason` at `crypto_gains_sheet.py:45-46` (written as `f"YES: {review_reason}"`) AND `CryptoReviewEntry.review_reason` at `crypto_supplementary_sheet.py:115`. Sanitization is therefore done UPSTREAM in the new module via a LOCAL helper `_sanitize_reason_text` (strip control chars; neutralize leading `= + - @`) - LOCAL, not imported from `application/persisting/excel_utils.py`, because importing a presentation-layer sanitizer into `application/crypto/` is a layer crossing; the char set MIRRORS `safe_cell_value` (cite it) so the two do not diverge. The load-bearing property is a **prose-prefix invariant**: every reason template leads with fixed literal prose (e.g. "Payment purchase:", "matched Payment for"), so no free-text external string ever lands at string position 0; only free-text external STRING fields (asset, wallet, platform) are routed through the helper, because numeric proceeds, calendar dates, and peg-fiat enum values are structurally incapable of carrying a formula sigil. A RED test asserts the FIRST CHARACTER of every emitted reason is alphabetic (binds the prose-prefix invariant directly, surviving template refactors).
7. **Gated and reversible; config is reused data, not hardcoded constants; loan-affected assets are skipped.** Behavior is controlled by `TaxJurisdictionConfig.infer_payment_proceeds` (DP-014). Flag off = today's behavior exactly (backward-compat, lesson #84). The orchestrator takes ONE injected kwarg `config: PaymentProceedsConfig` (bundling `payment_tags`, `stablecoins`, `stablecoin_pegs`) plus `loan_affected_assets: frozenset[str]` and the shared `review_entries` list - loaded from `docs/maintenance/tax/popular_crypto_tokens.json` by the wiring layer, so unit tests are hermetic. Entries whose asset is in `loan_affected_assets` are skipped (those are FIFO-rebuilt by `crypto_fifo/` with proceeds already computed; re-correcting them would double-handle the same TH Payment row). No payment-tag or stablecoin constant is hardcoded in code.
8. **Minimal, bounded rate threading - NOT the superseded generic rate plumbing.** The non-EUR-stablecoin fallback needs the fiscal year-end peg->EUR rate, so `Config.rates` (the already-loaded `list[ConversionRate]`, parsed once in `_main` from `[EXCHANGE RATES]`) is threaded as ONE bounded kwarg: `_main` -> `_load_crypto_tax_report(rates=app_config.rates if app_config is not None else None)` -> `load_koinly_crypto_report(rates=...)` -> the wiring derives a small `peg_to_eur_rates: dict[str, Decimal]` (one entry per peg currency that has an `[EXCHANGE RATES]` rate) and passes it to `correct_payment_proceeds`. This is deliberately NOT the superseded stablecoin-FMV design's `report_currency` + generic `rate_fn` plumbing (which converted ARBITRARY assets at ARBITRARY rates and had to be threaded as a callable through `_load_crypto_tax_report` / `_main`); here a single bounded rate dict, sourced from the same config shares/dividends use, drives ONLY the stablecoin-at-peg fallback. `transaction_history_file` and the local `review_entries` list already exist in `load_koinly_crypto_report`; only `rates` is newly threaded. `load_koinly_crypto_report` gains a `rates: list[ConversionRate] | None = None` kwarg (default `None` for backward compat), so `test_main_koinly_directory.py` needs a matching assertion update (Task 6). **`app_config` binding (r7 Blocker / r8 consistency):** `app_config` is bound only inside the `try` at `main.py:177`, and the config-load except (`:181-184`) warns-and-continues WITHOUT binding it, so `app_config` MUST be pre-bound `Config | None = None` at `~:176` (mirroring `tax_jurisdiction = None` at `:175`), and the call site MUST use the guarded form `rates=app_config.rates if app_config is not None else None` - a bare `app_config.rates` NameErrors on the config-missing + Koinly-present path. The guarded `None` is consumed downstream via `_derive_peg_to_eur_rates(rates or [], ...)`.

## Evaluation Criteria

**Quality dimensions:**
- Correctness: a payment disposal no longer carries a phantom full-cost loss. For a priced row, proceeds equals Koinly's `Net Value (EUR)` (gain = Net Value - cost). For an unpriced EUR-pegged stablecoin, proceeds equals the amount at par (gain ~= 0). Verified by data trace on the real motivating case (proceeds recovered, gain recomputed, not the phantom full-cost loss) recorded in the gitignored personal trace.
- Conservatism/safety: a non-zero `Net Value` is always used as-is (never overridden); the stablecoin fallback fires only when `Net Value == 0` AND the asset is a configured stablecoin - EUR-pegged -> amount at par, non-EUR-pegged WITH a config rate -> amount x year-end peg->EUR rate (both `review_required=True`); an unpriced non-EUR stablecoin with NO config rate and an unpriced non-stablecoin are both reviewed (never silently overwritten); a genuine zero-proceeds sale and any unmatched row are never overwritten; a count-matched collision blocks correction and surfaces a review entry.
- Robustness: CG<->TH correlation keys on (calendar-day + asset + platform + amount, not time) and is collision-safe via a per-key count-equality rule (`cg_count == th_count` -> correct one-per-event in order; counts differ, or no TH row -> skip + review for matched-but-ambiguous, plain skip for unmatched); it corrects same-calendar-day offsets only (a cross-midnight CG/TH offset falls to the DP-013 flag); a malformed/missing `Net Value` on one matched row blocks only that row (caught per-entry, including `decimal.InvalidOperation`), not the whole batch; the config loader degrades (never raises) on a missing/malformed/symlinked/oversize `popular_crypto_tokens.json` and warns when `stablecoin_pegs` drifts from `tokens.stablecoins`.
- Reversibility: gated by jurisdiction flag + DP-014; disabled state preserves existing behavior (dedicated backward-compat test).
- Personal-data hygiene: every tracked file (plan, tests, docs, the reused+extended JSON) is free of the user's real transaction data; the real trace lives only in gitignored `docs/maintenance/personal/`.
