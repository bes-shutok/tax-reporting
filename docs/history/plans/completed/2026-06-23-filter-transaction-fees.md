## Terminology & Abbreviations
- **SRG**: Structure Reporting Guideline (historically Shares Reporting Guideline) - rules for workbook layout, sheet structure, and auxiliary data source mapping in `docs/maintenance/tax_reporting_guidelines.md`.
- **CRG**: Crypto Reporting Guideline - guidelines for crypto data formatting and assumptions in `docs/maintenance/crypto_reporting_guidelines.md`.
- **PT-C**: Portugal Crypto Rule - country-specific crypto tax-law classification rules in `docs/maintenance/crypto_rules.md`.
- **DP**: Decision Point - country-scoped, year-versioned tax-law decision mappings config in `docs/maintenance/tax/decision_points/`.
- **CMD**: Crypto Mapping Decision - operator/platform origin and domicile registry in `docs/maintenance/tax/crypto-origin/`.

This plan implements the dynamic filtering of standalone network/transaction fee disposals (Koinly tag `Cost` or `Loan fee`) from the capital gains worksheets. Under jurisdictions like Portugal (CIRS Art. 10(1)(k)), standalone transaction fees are non-taxable utility costs without received consideration (rather than taxable alienações onerosas), and Koinly's default realization of gains on them must be filtered out.

Based on user feedback, some service payments (such as card fees or subscription costs) are also marked as `Cost` by Koinly. Furthermore, many transaction fees are not tagged with `Cost` or `Loan fee` by default in Koinly (they remain untagged withdrawals marked as `Send`), while the actual transacted assets (like `10 ZK` or `1031 PYTH`) are also untagged withdrawals under the same transaction hash.

To handle this safely without incorrectly filtering out taxable asset disposals, we define a two-pronged identification rule for network/transaction fees in the Transaction History:
1. **Explicitly Tagged Fees**: Any `crypto_withdrawal` tagged `Cost` or `Loan fee`. Only the co-occurrence guard applies - no amount threshold is needed since we trust the explicit tag.
2. **Untagged Whitelisted Fees**: Any untagged `crypto_withdrawal` (empty tag) whose asset is a key in `exclude_transaction_fee_max_eur_per_asset` (a `dict[str, Decimal]` - the keys ARE the whitelist) **and** whose `Net Value (EUR)` from the TH CSV is `≤` that asset's per-token ceiling (`per_asset[asset]`).

Per-token ceilings: ETH = 1.0 (ETH gas can realistically reach ~0.70 EUR), all other whitelisted assets = 0.5 (SOL, SUI, TON, BNB, MATIC fees are typically well under 0.50 EUR). The `dict` keys ARE the eligibility set - this prevents zero-priced LP/DeFi tokens (where Koinly emits `Net Value = 0.0`) from being misclassified as fees despite representing real asset disposals. Adding a new gas token later (e.g. BERA) is one config line (`BERA = 0.5`); per-token ceilings are supported by giving each key its own value. **Safe eligibility:** an unlisted asset is NEVER auto-filtered (it stays taxable - the safe over-tax direction). To avoid silently missing legitimate unlisted gas tokens, the scanner ALSO surfaces untagged, TxHash-co-occurring withdrawals whose asset is NOT in the dict and whose `Net Value (EUR) ≤ max(per_asset.values())` for manual review (not removal) - see Task 3.

## Gist & Examples

When `exclude_transaction_fees` is enabled for the tax jurisdiction:
1. We parse the Transaction History CSV and count each non-empty `TxHash`.
2. We identify **fee events** in the Transaction History CSV by scanning for rows with `Type == "crypto_withdrawal"` where:
   - Either `Tag` matches `Cost` or `Loan fee` - co-occurrence guard only, no amount check;
   - Or `Tag` is empty/missing, the `Sent Currency` is a key in `exclude_transaction_fee_max_eur_per_asset`, and the `Net Value (EUR)` column is `≤` that asset's per-token ceiling.
3. We identify **suspect events** (unlisted-asset fees to surface, never auto-filter): untagged `crypto_withdrawal` rows whose `Sent Currency` is NOT a dict key, AND whose `Net Value (EUR) ≤ max(per_asset.values())`, with co-occurrence guard. **Empty-dict guard (r6 M1, r11 wording):** when `exclude_transaction_fee_max_eur_per_asset` is empty, the suspect branch is skipped entirely (no `max()` call) and the untagged-whitelist branch finds nothing (no dict keys); the TAGGED `Cost`/`Loan fee` path is dict-INDEPENDENT and STILL filters, so an empty dict DEGRADES the filter to tagged-only - it is NOT a full no-op (Design Invariant 5).
4. **Correlation Guard**: We drop any fee or suspect event whose `TxHash` is empty or only occurs once in the Transaction History CSV (applies to BOTH tagged and untagged paths, fees AND suspects). This keeps standalone service payments and standalone asset transfers taxable.
5. Each surviving event is emitted as a `FeeThEvent(timestamp, asset, wallet, amount, tagged, tx_hash, net_value_eur)` where `wallet = normalize_platform_name(Sending Wallet)` and the first four fields satisfy the shared matcher's `ThEvent` Protocol (the remaining fields are for per-lot logging). The CG lot is keyed by its **raw stripped** `Wallet Name` (`CryptoCapitalGainEntry.wallet`, set at `crypto_reporting.py:547`), while the event's `wallet` is `normalize_platform_name(Sending Wallet)`; the two are equal only for non-ByBit, non-empty wallets. This raw-vs-normalized asymmetry is **inherited byte-identically from `derivatives_dedup`** (the shared matcher keys the lot by `lot.entry.wallet` and the event by `event.wallet`); matching must use `wallet`, not `platform` (`CryptoCapitalGainEntry.platform` = `normalize_platform_name(Wallet Name)` is the institution, NOT the blockchain).
6. **Fees are removed.** Fee events are matched to Capital Gains lots by the **shared two-phase matcher** (extracted from `derivatives_dedup`; see Task 2) using `(disposal_timestamp, asset, wallet, amount)` with minute precision:
   - **Phase 1 (Exact Match)**: Matches events to lots with the same 6-decimal-quantized amount.
   - **Phase 2 (Contiguous Range Fallback)**: Matches events to contiguous ranges of FIFO lots that sum to the event amount within a minor rounding tolerance.
   Matched fee lots are removed from the capital gains list (via `remove_matched_lots`).
7. **Suspects are surfaced, NOT removed** (they stay taxable). Suspect events are matched to CG lots via the shared matcher in a **match-only** mode (`match_lots`, Task 2 - same two-phase algorithm, no removal, no summary). For each CG-matched suspect lot, the fee module flags it via `dataclasses.replace(entry, review_required=True, review_reason=...)` (`CryptoCapitalGainEntry` is `@dataclass(frozen=True)`). For EVERY suspect (CG-matched or not), the fee module:
   - appends a `CryptoReviewEntry` to the threaded `review_entries` list (`source_section="capital_gains"` when the suspect matched a CG lot, else the new `"transaction_history"`) so it appears in the Crypto Supplementary "Review required" section;
   - logs a `logger.warning("Possible untagged fee for unlisted asset %s (Net Value %s EUR); not filtered. Add to exclude_transaction_fee_max_eur_per_asset if this is a fee.", ...)`.
   A brief aggregate suspect summary WARNING is emitted from the fee module when ≥1 suspect is found.
8. **Propagation to Crypto Gains (visibility):** aggregation preserves a lot-level `review_required` flag into the aggregated entry via `any(e.review_required for e in group)` (`aggregation.py:300`), so a flagged CG-matched suspect lot produces a red row plus `"YES: <reason>"` in the Crypto Gains worksheet. The `CryptoReviewEntry` list is the **robust backstop**: it is appended in place to `review_entries` (created `crypto_reporting.py:155`, rendered `crypto_supplementary_sheet.py:247`) and reaches the Supplementary sheet regardless of any flag-propagation step. Suspects WITHOUT a CG line (pure transfer fees Koinly never realized) appear only in Supplementary + the log.
9. **Summary:** `remove_matched_lots` emits exactly one aggregate summary WARNING per fee pass (called with `domain_label="fee"`, which `.title()` renders as `"Fee CG dedup summary"` in the message text - see Task 2) for the removed-fee lots and any collisions/surplus (lesson #108/#119).

### Example:
- **TH row 1 (Main Transfer)**: `Date`: `2025-03-30 12:00:00 UTC`, `Type`: `transfer`, `TxHash`: `0xaeae2f...`
- **TH row 2 (Fee)**: `Date`: `2025-03-30 12:00:00 UTC`, `Type`: `crypto_withdrawal`, `Tag`: `Cost`, `Sent Amount`: `0.00267371`, `Sending Wallet`: `MetaMask`, `TxHash`: `0xaeae2f...`
  *Since `0xaeae2f...` occurs twice in TH, the correlation guard passes. The fee event's `wallet = normalize_platform_name("MetaMask")`.*
- **CG entries** (due to FIFO lot splits):
  - Lot 1: Disposal `2025-03-30 12:00` (UTC), Asset `ETH`, Wallet `MetaMask`, Amount `0.00200000`, Cost `0.50 EUR`, Proceeds `1.50 EUR`, Gain `1.00 EUR`.
  - Lot 2: Disposal `2025-03-30 12:00` (UTC), Asset `ETH`, Wallet `MetaMask`, Amount `0.00067371`, Cost `0.15 EUR`, Proceeds `0.50 EUR`, Gain `0.35 EUR`.
- **Outcome**: The total amount of the two lots (`0.00200000 + 0.00067371 = 0.00267371`) matches the TH withdrawal event. Both lots are filtered out.

### Suspect example (unlisted asset, surfaced not removed):
- **TH row 1 (Main Transfer)**: `Type`: `transfer`, `TxHash`: `0xbeef00...`
- **TH row 2 (Suspect gas fee)**: `Type`: `crypto_withdrawal`, `Tag`: empty, `Sent Currency`: `BERA`, `Net Value (EUR)`: `0.30`, `Sending Wallet`: `MetaMask`, `TxHash`: `0xbeef00...`. `BERA` is not a dict key and `0.30 ≤ 1.0` (max ceiling), so this is a **suspect**, not a fee.
- **Outcome**: no CG lot is removed. If a CG lot exists for the BERA disposal at the same timestamp/wallet/amount, it is flagged `review_required=True` (red row in Crypto Gains); a `CryptoReviewEntry` (source "Transaction History", or "Capital Gains" if CG-matched) is added to Supplementary; a WARNING is logged. The user verifies and, if it is indeed a gas fee, adds `BERA = 0.5` to the config so a future run filters it.

## User Review Required

> [!IMPORTANT]
> **TxHash Co-occurrence, Per-Token EUR Ceiling Rules**:
> - We require a transaction to have a non-empty `TxHash` that appears at least twice in the Transaction History CSV to be classified as a network fee or a suspect (tagged, untagged-fee, and suspect paths).
> - **Tagged `Cost`/`Loan fee`**: co-occurrence guard only - the explicit tag is trusted, no amount threshold applied. Removed.
> - **Untagged fee**: co-occurrence guard **plus** the asset must be a key in `exclude_transaction_fee_max_eur_per_asset` and its `Net Value (EUR)` must be `≤` that asset's per-token ceiling (ETH = 1.0; SOL/SUI/BNB/MATIC/TON = 0.5). Removed. This prevents zero-priced non-whitelisted LP/DeFi tokens from being filtered and limits accidental filtering of real small-asset disposals (e.g. `10 ZK` ≈ 1 EUR is not a dict key, so it stays taxable).
> - **Suspect (unlisted asset)**: co-occurrence guard plus the asset is NOT a dict key and `Net Value (EUR) ≤ max(per_asset.values())`. NOT removed. Surfaced for review (Crypto Gains red flag if it has a CG line, plus a Crypto Supplementary row, plus a log WARNING) so legitimate gas tokens missing from the config (e.g. BERA) can be discovered and added without under-tax risk. Skipped entirely when the dict is empty.

> [!NOTE]
> **Confirmed values (2026-06-23):** `exclude_transaction_fee_max_eur_per_asset` = `{ETH: 1.0, SOL: 0.5, SUI: 0.5, BNB: 0.5, MATIC: 0.5, TON: 0.5}`. Per-token ceilings; ETH=1.0 is the only override. These are hardcoded config values flagged and confirmed with the user per the hardcoded-value rule.

> [!IMPORTANT]
> **Accepted Risk - cross-tx match (r7 M4 / r8 Mon1):** the correlation guard validates the fee EVENT's TxHash multiplicity (≥ 2 occurrences in TH), NOT the correspondence between the fee's TxHash and the matched CG lot's origin. `CryptoCapitalGainEntry` carries no TxHash, so the matcher keys lots to events by `(minute, asset, wallet, amount_6dp)` only and can, in principle, match the wrong lot when a tagged fee shares a TxHash with a transfer while an UNRELATED same-minute/wallet/amount disposal exists - silent lost tax, the worst direction for a tax report. Enforcing correspondence requires plumbing TxHash onto CG lots, which is out of scope for DP-015. This residual risk is ACCEPTED on three grounds: (a) a RED test pins the intended happy path; (b) the matcher cannot be made to fail here, so the risk is observed rather than enforced; (c) the fee module's per-lot INFO/WARNING log records each removed lot's identity tuple `(disposal_timestamp, asset, wallet, amount)` + the fee's TxHash, so a cross-transaction match is visible during the release-gate spot-check. If the user requires hard enforcement, that is a follow-up to add TxHash to `CryptoCapitalGainEntry`.

## Design Invariants

1. **Matcher reuse (rule #119):** the fee filter and `derivatives_dedup` are sibling TH-event→CG-lot matchers performing the same conceptual operation; both must use the shared matcher in `th_lot_matcher.py`. The matcher reads only `event.timestamp/.asset/.wallet/.amount` and is generic over the event type.
2. **Callback seam (r5 Blocker):** the shared matcher owns the algorithm AND the single summary WARNING (emitted via the caller-passed `logger`, text parameterized by `domain_label`); per-lot INFO logging is CALLER-owned; the matcher NEVER references `event.label`. `domain_label` parameterizes message TEXT only; the caller passes its own `logger` so the record carries the caller's module logger name.
3. **Safe eligibility:** only whitelisted (dict-key) assets are auto-filtered. Unlisted assets are NEVER removed; suspects are surfaced (flag + Supplementary + log) for manual triage. Over-taxing on uncertainty is the safe direction. **r7 M5:** untagged-whitelisted removals (which CAN misclassify a genuine whitelisted-asset dust disposal as a fee, since both have sub-ceiling `proceeds_eur`) are NOT silent - each emits a distinct `logger.warning` naming asset + **Net Value (EUR)** (`FeeThEvent.net_value_eur`, r8 M2) + TxHash so the user can catch a misclassified disposal during the release-gate spot-check. (A `proceeds_eur`-based predicate to narrow the untagged-whitelisted path was considered and rejected: a network fee disposal and a dust disposal both have proceeds ≈ Net Value ≤ the ceiling, so it would not discriminate them, and it would change behavior the user already confirmed.)
4. **Suspect-flag propagation:** the lot-level `review_required` flag set on a CG-matched suspect must reach the final aggregated entry to drive the Crypto Gains red row. Aggregation preserves it via `any()` (`aggregation.py:300`) and joins `review_reason` (`:301`). OGR direction override rebuilds its result 1:1 in input order (`crypto_reporting.py:273-274`), preserving lot fields (`ogr_handler.py:494-501` omits `review_required`/`review_reason` from its `replace`, so the flag survives - guarded by the r7 L4 test). `correct_payment_proceeds` appends non-candidate lots unchanged (`payment_proceeds.py:616/624`). **[r11 Blocker: Option D Split Fee Pass]** To prevent `correct_payment_proceeds` from clobbering the fee-suspect flag or producing contradictory reasons (e.g. joining a 'Zero disposal proceeds' parse-time reason with the payment-proceeds reason), we run suspect flagging *after* `payment_proceeds` and *before* aggregation. The pipeline is: `dedup -> fee_removal (early) -> OGR -> re-zero -> payment_proceeds -> fee_suspect_flagging (late) -> aggregation -> materiality`. Thus, any proceeds corrections are complete when the suspect pass runs, keeping `payment_proceeds.py` completely unchanged and avoiding any reason-joining logic there. The pinning test asserts the final aggregated entry's `review_reason` is exactly the fee-suspect reason (no payment-proceeds reason needs to be joined since they represent different disposals, and payment proceeds does not touch suspect flag status).
5. **Empty-dict safety (r6 M1, r11 wording):** `max(per_asset.values())` raises `ValueError` on an empty dict. When the flag is enabled but the dict is empty (a country that enables the flag without listing tokens, or a misconfiguration), the suspect branch is skipped entirely (explicit `if per_asset:` guard) and the untagged-whitelist branch finds nothing (no dict keys); the TAGGED `Cost`/`Loan fee` path is dict-INDEPENDENT (Gist step 1) and STILL filters. The filter therefore DEGRADES to tagged-only under an empty dict - it is NOT a full no-op (correcting the earlier "whole filter is a no-op" wording, which was false for the tagged path). No `max()` call is ever made on an empty dict.
6. **Backward compatibility (lesson #84):** `exclude_transaction_fees = False` and `jurisdiction is None` and missing file are all no-ops returning `capital_entries` unchanged.
7. **Same-txhash correspondence is assumed, not enforced (r7 M4, r8 Mon1):** the correlation guard validates the fee EVENT's TxHash multiplicity (≥ 2), not the correspondence between the fee's TxHash and the matched CG lot's origin - `CryptoCapitalGainEntry` carries no TxHash, so the matcher keys lots to events by `(minute, asset, wallet, amount_6dp)` only. A tagged fee sharing a TxHash with a transfer while an UNRELATED same-minute/wallet/amount disposal exists could therefore match the wrong lot (silent lost tax). The matcher cannot cheaply verify correspondence without plumbing TxHash onto lots (out of scope). Mitigations: a RED test (`test_per_lot_log_records_removed_lot_identity_for_cross_tx_spot_check`) pins the intended behavior, and the fee module's per-lot INFO log records the matched lot's `(disposal_timestamp, asset, wallet, amount)` - read via `lot.entry.*`, NOT bare `lot.*` (r8 M1) - alongside the fee event's TxHash so a cross-transaction match is visible during the release-gate spot-check. The residual risk is an explicit Accepted Risk (see User Review Required).

## Evaluation Criteria

**Quality dimensions:**
- **Correctness**: Tagged `Cost`/`Loan fee` withdrawals are filtered regardless of EUR amount; untagged whitelisted withdrawals are filtered only when EUR value ≤ the asset's per-token ceiling; all other withdrawals remain taxable. Correlation guard (TxHash ≥ 2 occurrences) is applied to fees and suspects. An empty ceiling dict never crashes the filter.
- **Safety**: Zero-priced withdrawals of **non-whitelisted** assets (LP/DeFi tokens absent from the dict) are never filtered via the untagged path. Zero-priced withdrawals of **whitelisted** assets (e.g. SOL at 0.0, a genuine gas fee) ARE filtered because `0.0 ≤` the ceiling. Real small-asset disposals of non-whitelisted assets (e.g. `10 ZK` ≈ 1 EUR) are never silently dropped.
- **Discoverability (visibility)**: Untagged, TxHash-co-occurring withdrawals of assets NOT in the dict, with `Net Value (EUR) ≤ max(per_asset.values())`, are surfaced (a) as a log WARNING naming the asset and its Net Value (EUR), (b) as a Crypto Supplementary "Review required" row, and (c) when they correlate to a CG lot, as a red `review_required` flag on that lot propagating to a "YES: <reason>" red row in Crypto Gains (only when the aggregated `|gain_loss| ≥ 1 EUR`, else materiality drops it and it appears in Supplementary/log only). They are never silently filtered, never silently ignored. **[r7 M5]** Untagged-WHITELISTED removals (which can misclassify a genuine dust disposal) are also non-silent: each emits a per-lot WARNING (vs INFO for trusted tagged removals) naming asset + Net Value (EUR) (`event.net_value_eur`) + TxHash.
- **Test coverage**: All identification paths (tagged-fee, untagged-fee-pass, untagged-fee-fail, untagged-co-occurrence-fail, unlisted-suspect-flag, unlisted-suspect-boundary, empty-dict-no-op), the ETH override band, both matching phases (exact, contiguous range), suspect CG-flag propagation, and suspect CryptoReviewEntry creation have dedicated RED→GREEN test cases, plus disabled-state no-op tests.
- **Non-regression**: Full `uv run pytest` suite passes after each task commit (derivatives dedup tests stay green after the matcher extraction, including the per-lot INFO and summary WARNING logger-name assertions in `test_crypto_derivatives_separation.py`). basedpyright reports no `ThEvent has no attribute "label"` error on the derivatives per-lot log (r6 M2).
- **Config safety**: Non-PT countries that omit `exclude_transaction_fee_max_eur_per_asset` from their TOML default to an empty dict (no filtering); the flag `exclude_transaction_fees = false` is the global default. The bool-default loop touches only bool-typed fields; the dict field defaults via `default_factory`.
