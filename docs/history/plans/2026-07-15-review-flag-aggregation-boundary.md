## Terms

- **Aggregated review flag** - the `review_required` / `review_reason` shown on a user-visible row in the Excel report. Distinct from a per-lot or per-source-row flag, which lives inside the in-memory entry list and never reaches the user directly.
- **Zero-basis review** - per-lot flag fired when a disposal lot has `cost_eur == 0`. Already in glossary; this plan refines *where* it is re-evaluated.
- **Reward dust** - a reward-income row whose Koinly-exported `Value (EUR)` rounds to `0,00` because the reward's true EUR value is below €0.005, *not* because the price feed is missing. Distinct from a genuinely unpriced reward (no price feed exists for the asset).
- **In-asset interest** - loan repayment overshoot that occurs when a DeFi variable-rate loan accrues interest in the borrowed asset, so `repaid_amount` exceeds `received_amount` by a small percentage with no cross-year anomaly.
- **Popular asset** - an asset matched by `_get_popular_crypto_tokens()` or `_contains_popular_token(asset)` from `application/crypto/classification.py`. This is the discriminator available at sheet-render time. `CapitalGainsParsingContext.known_assets` is NOT available at the sheet layer (it lives on the parse context, not on `TaxJurisdictionConfig`), so it is intentionally excluded from this discriminator; a row whose asset is in `known_assets` but not in the popular-token set will be treated as niche and keep the per-row YES flag.
- **Zero-basis reason prefix** - any user-facing review reason whose rendered text starts with `"Zero EUR value for known crypto asset"`, `"Zero acquisition cost"`, or `"Zero disposal proceeds"`. The aggregated-row filter strips reasons by stable prefix rather than by full-string equality, so minor wording edits to the upstream literals (e.g. rewording `"likely Koinly tracking entry or data error"`) do not silently break the strip set.
- **Sentinel + detail split (loan status)** - `LoanActivityEntry.balance_status` is a closed set of sentinel constants (`LOAN_STATUS_SETTLED`, `LOAN_STATUS_OPEN_LOAN`, `LOAN_STATUS_IN_ASSET_INTEREST`, `LOAN_STATUS_NO_EUR_PRICE`, `LOAN_STATUS_OVERPAID_VERIFY`). Any varying text (e.g. overshoot percentage) goes in a new sibling `balance_detail: str | None` field. The Excel sheet's fill-color logic matches on the sentinel, never on the rendered string.

## Gist & Examples

### Problem

Three review flags in the crypto Excel export fire on rows where the underlying signal is stale relative to the user-visible aggregated state:

1. **Crypto Gains - "Zero EUR value…" / "Zero acquisition cost…" on aggregated disposals.** `_aggregate_capital_entries` (`aggregation.py:330-331`) computes the aggregated row's `review_required` as `any(lot.review_required for lot in group)` and joins every lot's `review_reason`. A single noisy lot (e.g. one Koinly `FEE` tracking entry, or one reward lot with no price data) inside a 109-lot disposal poisons the aggregated row's flag even when the aggregated `cost_eur`, `proceeds_eur`, and `gain_loss_eur` are all non-zero and material. Four such rows appear in the 2025 export.
2. **Crypto Supplementary - "Zero EUR value…" on 2 490 reward rows.** `_parse_income_file` (`crypto_reporting.py:1010-1021`) fires the flag whenever `value_eur == 0` on a popular asset. 1 472 of the zero-value rows are sub-cent dust on BNB / USDT / USDC / ETH / SOL rewards (e.g. `0.00000569 BNB`, true value ≈ €0.003) - Koinly rounds to 2 decimals in the export. These are not missing-price cases. The remaining ~810 rows (OSBGT, XFATBERA, EWBERA-4, PBERA, SWBERA, BGT, STBGT, …) are genuinely unpriced and the flag is correct.
3. **Loan Activity - "Overpaid (cross-year loan?)" on 2 rows.** `_extract_loan_activity` (`loan_activity.py:108-112`) labels any asset with `received_amount − repaid_amount < 0` as cross-year. In the 2025 export both flagged rows (LBTC overshoot 0.36%, WBTC overshoot 0.59%) are in-asset interest, not cross-year principal. LBTC additionally has `received_value_eur == 0` for every row, so no EUR-based classification is possible at all.

### Fix principle (shared)

Re-evaluate each review signal against the user-visible aggregated state, not the per-lot / per-source-row state. The per-lot signal stays in the in-memory entry list (and the per-lot log warnings), but the flag rendered on the aggregated row is re-derived from the aggregated values.

## Evaluation Criteria

**Quality dimensions:**

- **Correctness (signal preservation):** when *every* lot in an aggregated disposal is all-zero, the flag still fires. When only some lots are noisy, the aggregated flag is dropped iff aggregated `cost > 0 AND proceeds > 0 AND |gain| >= _MATERIALITY_THRESHOLD`. Verified by unit tests covering both branches.
- **Correctness (non-zero-basis reasons preserved):** reasons unrelated to zero-basis (phantom lot, operator-origin review, homoglyph, OGR override, missing-cost-basis-with-impact, foreign-tax parse failure) survive aggregation unchanged. Verified by a per-reason parametrized test.
- **Correctness (reward dust vs unpriced):** the dust summary fires only when the asset is popular; niche tokens with `value_eur == 0` keep the per-row YES flag. Verified by tests on both sides of the popular-asset discriminator.
- **Correctness (loan classification):** four fill behaviors across five sentinel constants - small-overshoot-with-EUR (`LOAN_STATUS_IN_ASSET_INTEREST`, neutral), no-EUR-price (`LOAN_STATUS_NO_EUR_PRICE`, yellow), large-overshoot (`LOAN_STATUS_OVERPAID_VERIFY`, red), and repayment-only with `received_amount == 0` (`LOAN_STATUS_OVERPAID_VERIFY`, red, treated as unbounded overshoot). Each emits the correct sentinel and fill. Verified by parametrized tests at the boundary (0.99%, 1.00%, 1.01%) and a dedicated `received_amount == 0` test.
- **Non-regression:** existing `_aggregate_capital_entries` tests (`tests/unit/application/test_crypto_reporting.py` line 928+, 21 cases) continue to pass without modification *except* the cases this plan intentionally changes (mixed-lot aggregated flag, all-zero-lot aggregated flag); those are updated in-task with a cited design invariant.
- **Maintainability:** no new public API surface beyond one module-level symbol (`LOAN_OVERSHOOT_INTEREST_PCT` in `loan_activity.py`, consumed by tests and `_extract_loan_activity`). The Task 1 filter is inlined as a private helper inside `aggregation.py` (single caller, single source of truth for `_MATERIALITY_THRESHOLD`); sheet-writing logic stays where it is.
- **Observability:** dropped per-lot noise still appears in `context.review_entries` and the WARNING log; the Excel row is the only thing cleaned up. No data is silently lost.

## Design Invariants (CR Guard)

1. **Per-lot signal preservation.** The lot-level `review_required` / `review_reason` on `CryptoCapitalGainEntry` and `CryptoFifoRealization` MUST remain set as today; this plan only changes how the *aggregated* row's flag is computed. The per-lot review list (`context.review_entries`) and WARNING logs are not silenced.
2. **Filter owns both aggregated fields atomically.** `_re_evaluate_aggregated_review` returns `(review_required, review_reason)` and `_aggregate_capital_entries` MUST apply BOTH fields from the filter's return in a single `replace(...)` call. `CryptoCapitalGainEntry.__post_init__` (`entities.py:390-393`) raises `ValueError` on the inconsistent pair `review_required=True AND review_reason=None`; partial application of the filter (e.g. updating `review_reason` but leaving `review_required` from the `any(...)` reduction) crashes the pipeline. The filter is the single source of truth for both fields on the aggregated entry. The helper is inlined as a private function inside `aggregation.py` (single caller, reuses `_MATERIALITY_THRESHOLD` without a cross-module import). **The helper body MUST start with `if entry.review_reason is None: return (entry.review_required, entry.review_reason)`**  -  the materiality gate depends only on numeric fields, and the aggregated `review_reason` is `None` on the default clean-disposal path (every lot has `review_required=False`, producing `"; ".join(...) or None` = `None` at `aggregation.py:331`). Without this guard, `None.split("; ")` crashes the pipeline on the first material clean disposal. Dedicated test: `test_none_review_reason_with_material_values_returns_unchanged`.
3. **Materiality gate is the existing `_MATERIALITY_THRESHOLD = Decimal("1")`.** Do not introduce a second materiality constant; reuse the same one that `_filter_immaterial_entries` uses.
4. **Reward dust is bounded by Koinly's 2-decimal export.** The dust discriminator is `value_eur == 0` on the parsed entry AND asset matches `_get_popular_crypto_tokens() ∪ _contains_popular_token(asset)`. `CapitalGainsParsingContext.known_assets` is NOT available at sheet render time; do not thread it through. Do not compute a "true pre-rounding value" - the source no longer has it. The summary line tells the user to re-export with higher precision if they want certainty.
5. **Loan Activity classification uses amount-space overshoot, not EUR-space.** EUR values are 0 for LBTC and any asset Koinly didn't price. The percentage is `abs(repaid_amount − received_amount) / received_amount × 100`. The classifier has FOUR branches evaluated in this exact precedence order: (b) FIRST `received_amount == 0 AND repaid_amount > 0` → `LOAN_STATUS_OVERPAID_VERIFY` (red; repayment-only asset - overshoot is unbounded; this wins over (a) because a repayment-only asset is the stronger anomaly even when no EUR price exists); (a) THEN `received_value_eur == 0` → `LOAN_STATUS_NO_EUR_PRICE` (yellow); (c) THEN `overshoot_pct <= LOAN_OVERSHOOT_INTEREST_PCT` → `LOAN_STATUS_IN_ASSET_INTEREST` (neutral); (d) OTHERWISE → `LOAN_STATUS_OVERPAID_VERIFY` (red). Note: a repayment-only asset DOES enter `accs` via `loan_activity.py:99-103`, so branch (b) is reachable - the prior claim "the row would not exist in `accs` in that case" was wrong.
6. **`LOAN_OVERSHOOT_INTEREST_PCT = Decimal("1")` is a module-level constant in `loan_activity.py` (no underscore, no re-export).** Tests import it directly from `loan_activity.py`. Do not put it in `domain/constants.py`; it is a classification-layer threshold consumed by `_extract_loan_activity`, co-located with its sole production caller. `domain/constants.py` is reserved for cross-module business constants. Per CLAUDE.md "never introduce a hardcoded value without first flagging it" - flagged at design time, user-approved.
7. **`balance_status` is a sentinel; varying text goes in `balance_detail`.** The Excel sheet's fill-color mapping matches `entry.balance_status == LOAN_STATUS_<BUCKET>` (exact equality against a constant). The overshoot percentage is rendered from `entry.balance_detail` (e.g. `"overshoot 0.5853%"`) into a sibling cell, NOT interpolated into `balance_status`. This decouples classification semantics from presentation severity.
8. **No silent data loss.** Suppressing a per-row flag MUST either (a) keep the row visible (Loan Activity, Crypto Gains aggregated row) or (b) keep a summary line (Crypto Supplementary dust). The total count of suppressed rows must be visible somewhere on the rendered sheet. Section 4 of `crypto_supplementary_sheet.py` MUST reconcile: split the existing "Taxable-now rows (immediately taxable)" reconciliation row into "Taxable-now detail rows" and "Taxable-now dust rows (suppressed from detail)" so a reviewer cross-checking counts cannot conclude data is missing.
